DBMS Mini Project – Smart Restaurant Ordering, Reservation and Management System 
1. Problem Statement 
Problem Statement: Design and implement a database-driven restaurant management system that enables 
customers and restaurant staff to efficiently manage menu items, table reservations, food orders, payments 
and operational records while maintaining data consistency and integrity. 
2. Problem Description 
The proposed system is designed for restaurant customers, staff and administrators to simplify day-to-day 
restaurant operations. Customers can browse the menu, reserve tables, place food orders, make payments 
and provide feedback. Restaurant staff can manage table availability, reservations, orders and customer 
service, while administrators can maintain menu, staff and transaction records. 
The SQL database stores structured and transactional data such as Customer, Staff, Restaurant Table, 
Reservation, Category, Menu Item, Order, Order Item and Payment. The project is designed so that MongoDB 
can later be used for flexible data such as reviews, customer preferences and order customizations. The core 
SQL database must support queries such as finding available tables for a specific capacity, retrieving a 
customer's order history, calculating an order bill and identifying the most popular menu items. 
Target Users 
• Customers – browse the menu, make reservations, place orders and view bills. 
• Restaurant Staff – manage reservations, tables and order status. 
• Administrators – manage menu categories, menu items, staff and restaurant records. 
Core Entities 
• Customer 
• Staff 
• Restaurant_Table 
• Reservation 
• Category 
• Menu_Item 
• Orders 
• Order_Item 
• Payment 
Key Database Queries 
• Find tables that are available for a required capacity and reservation time. 
• Retrieve the complete order history of a particular customer. 
• Display all items and calculate the total bill for an order. 
• Find the most popular menu items based on quantity sold.

6. Normalization to 3NF 
The relational design is structured to satisfy Third Normal Form (3NF). Normalization reduces redundancy and 
prevents insertion, update and deletion anomalies. 
First Normal Form (1NF) 
All attributes contain atomic values and there are no repeating groups. For example, multiple items in an order 
are not stored as item1, item2, item3 columns. They are represented as separate rows in ORDER_ITEM. 
Second Normal Form (2NF) 
Non-key attributes depend on the whole primary key. ORDER_ITEM has a composite primary key (order_id, 
item_id), and quantity and unit_price describe that particular order-item combination.

Third Normal Form (3NF) 
There are no transitive dependencies among non-key attributes. For example, category_name is stored in 
CATEGORY rather than MENU_ITEM, and customer contact information is stored in CUSTOMER rather than 
ORDERS. Therefore, non-key attributes depend on the key, the whole key and nothing but the key. 
Examples of Decomposition 
• Customer details are separated from Orders using customer_id. 
• Menu category information is separated from Menu_Item using category_id. 
• The M:N relationship between Orders and Menu_Item is decomposed through Order_Item. 
• Payment details are separated from Orders using order_id.

Query 4 – Find the five most popular dishes 
SELECT 
    m.item_name, 
    SUM(oi.quantity) AS total_quantity_sold 
FROM Menu_Item m 
JOIN Order_Item oi 
    ON m.item_id = oi.item_id 
JOIN Orders o 
    ON oi.order_id = o.order_id 
WHERE o.status <> 'Cancelled' 
GROUP BY m.item_id, m.item_name 
ORDER BY total_quantity_sold DESC 
LIMIT 5;

10. SQL Triggers 
Triggers are used to enforce important business rules automatically at the database level. Two triggers are 
included: automatic maintenance of order totals and prevention of duplicate reservations for the same table, 
date and time. 
Trigger 1 – Automatically Update Order Total 
Whenever an Order_Item is inserted, updated or deleted, the corresponding Orders.total_amount is 
recalculated from the current order items. 
CREATE OR REPLACE FUNCTION update_order_total() 
RETURNS TRIGGER AS $$ 
BEGIN 
    IF TG_OP = 'DELETE' THEN 
        UPDATE Orders 
        SET total_amount = ( 
            SELECT COALESCE(SUM(subtotal), 0) 
            FROM Order_Item 
            WHERE order_id = OLD.order_id 
        ) 
        WHERE order_id = OLD.order_id; 
 
        RETURN OLD;

    ELSE 
        UPDATE Orders 
        SET total_amount = ( 
            SELECT COALESCE(SUM(subtotal), 0) 
            FROM Order_Item 
            WHERE order_id = NEW.order_id 
        ) 
        WHERE order_id = NEW.order_id; 
 
        RETURN NEW; 
    END IF; 
END; 
$$ LANGUAGE plpgsql; 
 
CREATE TRIGGER trg_update_order_total 
AFTER INSERT OR UPDATE OR DELETE 
ON Order_Item 
FOR EACH ROW 
EXECUTE FUNCTION update_order_total(); 
 
Purpose: keeps the total amount in Orders synchronized with Order_Item records without requiring the 
application to manually recalculate the total after every change. 
Trigger 2 – Prevent Reservation Conflict 
Before inserting or updating a reservation, the trigger checks whether the selected table is already reserved for 
the same date and time. 
CREATE OR REPLACE FUNCTION check_reservation_conflict() 
RETURNS TRIGGER AS $$ 
BEGIN 
    IF EXISTS ( 
        SELECT 1 
        FROM Reservation 
        WHERE table_id = NEW.table_id 
          AND reservation_date = NEW.reservation_date 
          AND reservation_time = NEW.reservation_time 
          AND status = 'Confirmed' 
          AND reservation_id <> COALESCE(NEW.reservation_id, -1) 
    ) THEN 
        RAISE EXCEPTION 
        'Table % is already reserved at the selected date and time', 
        NEW.table_id; 
    END IF; 
 
    RETURN NEW; 
END; 
$$ LANGUAGE plpgsql; 
 
CREATE TRIGGER trg_check_reservation_conflict 
BEFORE INSERT OR UPDATE 
ON Reservation 
FOR EACH ROW 
EXECUTE FUNCTION check_reservation_conflict(); 
 
Purpose: prevents two confirmed reservations from being created for the same table at the same date and 
time.
